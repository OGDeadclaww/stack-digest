### 2026-09-22 — Sloth Bytes
- **Lesson:** Idempotency in one line: an operation is idempotent if running it once or ten times leaves the same result — HTTP's `GET`/`PUT`/`DELETE` are supposed to be idempotent, `POST` isn't, which is exactly where duplicate-charge bugs hide. Four concrete fixes: send the final state instead of a delta (`PUT quantity: 3`, not "add 1", so a lost-response retry doesn't pile up); block duplicates with a DB unique constraint (stops duplicate rows, not duplicate side effects like repeat notifications); guard one-time actions with an atomic check-and-update (`UPDATE ... WHERE bonus_claimed = false`) instead of check-then-write, which race-conditions under concurrent requests; or attach an idempotency key so a retry with the same key returns the original result instead of repeating the effect (Stripe, Resend, Inngest, Trigger.dev, and AWS Lambda Powertools all support this natively). [slothbytes.dev](https://www.slothbytes.dev/p/idempotency-for-dummies)

### 2026-09-17 — Sloth Bytes
- **Lesson:** Decompilation rebuilds readable high-level code from a compiled binary: a disassembler turns machine code into assembly for the target CPU (x86-64 vs ARM64 matters), then a decompiler traces control flow and value origins to reconstruct ifs/loops/expressions — but compiler optimizations and information loss (e.g. `coins++` vs `coins += 1` compile identically) mean it's a rebuild, not a guaranteed recovery of the original source, so treat its output as a lead to verify, not ready-to-compile code. Pick the tool by target: [Ghidra](https://github.com/NationalSecurityAgency/ghidra) for machine code (C/C++), [ILSpy](https://github.com/icsharpcode/ILSpy) for .NET/C#; distinct from static recompilation (translating instructions to run elsewhere) and emulation (reproducing another system's behavior at runtime).

### 2026-09-02 — Sloth Bytes
- **Lesson:** "Software factory" pattern in production (Vercel, Uber, Cloudflare+Astro, Warp, Stripe "Minions", Cursor, Shopify "River", Ramp "Inspect", PostHog, Spotify "Honk", Cognition/Devin): event in (issue/Slack/Sentry/Linear) → agent triages → agent implements in a sandbox and runs tests → another agent reviews the diff and scores risk → PR opened → a human (or confident agent) merges. "Lights on" (human merges — nearly everyone) vs "lights off" (agent merges, no human ever reads the diff — StrongDM's Attractor is the notable example). Dex Horthy (HumanLayer) ran lights-off for 4 months with zero review and the codebase rotted so badly one bug took weeks to untangle — models optimize for tests passing, not for code a human can still work in later. The one rule everyone agrees on: start with one small, boring job, get it reliable, measure for a few weeks, then add the next station.
- **Tool:** Software-factory starter kits: Vercel's [eve template](https://github.com/vercel-labs/eve-software-factory-template) (4-agent classifier/analyzer/implementer/reviewer, one-click deploy), Astro's [triagebot-action](https://github.com/withastro/triagebot-action) (label-driven state machine on GitHub Actions — good one to read first), [Warp Factories](https://docs.warp.dev/factories/how-factories-work/) ("factories-as-code", closed beta), StrongDM's [Attractor](https://github.com/strongdm/attractor) (the lights-off agent referenced above).
